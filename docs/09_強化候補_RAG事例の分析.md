# DefectReport AI 強化候補 — 文書検索 RAG の事例分析

別の文書検索 RAG システム(規則や様式を AI チャットで検索する事例)の設計と実測記録を分析し、
**DefectReport AI(今のシステム)に移植すると効果が見込める要素**を抽出したもの。(2026-09-05 調査)

**分析した事例の特徴**: 文書を自動収集し、ローカルLLM(Ollama)で要約・関連度判定して、規則や様式を
AIチャットで検索できるシステム。自作の検索サーバー(形態素BM25+意味検索)を持ち、**決定論的ベンチマーク
(100クエリ×6パターン)による検索チューニングの実測記録**と RAGAS/Langfuse 連携の評価基盤を持つのが特徴。

---

## 優先度A: すぐ効く(実測の裏付けあり) — **A-1/A-2/A-3 は 2026-09-05 実装済み(`services/hybrid.py`)**

### A-1. ハイブリッド検索(形態素BM25 + 密ベクトル + RRF融合)
- **現状**: DefectReport AI は Chroma の密ベクトル検索のみ(埋め込み未導入時はキーワード検索へフォールバック)
- **先方の実測**(`docs/retrieval_tuning.md`): 密のみ nDCG 0.637 に対し、SudachiPy形態素BM25+密+ドメイン知識の
  自作ハイブリッド検索は **nDCG 0.704 / R@1 0.591**。OpenSearch のハイブリッドすら上回る
- **移植**: 検索サーバーの BM25(SudachiPy トークン化)+RRF融合部を `report_service.py` の検索に追加。
  不良報告は件数が少ない(数百〜数千)ので numpy 全探索で十分(先方も 4,445チャンクで 3.4ms)
- **セミナー対応**: 第4回「精度改善のチューニング」の実例として最適

### A-2. 同義語辞書による表記揺れ対策
- **現状**: 「キズ/傷/疵」「バリ/ばり」「寸法不良/寸法NG」の揺れは埋め込み頼み
- **先方**: 同義語辞書(JSON)+ Sudachi の同義語辞書でクエリ正規化。kuromoji素のBM25が R@1 0.406 に
  沈む一方、この日本語処理こそが勝因だったと結論
- **移植**: 製造用語の同義語辞書(不良名・機械名・工程名)を `synonyms.json` 形式で作り、検索前にクエリ展開。
  LLMで下書き生成→人がレビューする半自動生成の仕組み(`synonyms_generated.json`/`synonyms_rejected.json`)も流用可

### A-3. 軽量オントロジー(ファセット)層 — LLMを使わない属性判定
- **先方の課題**: 「常勤版/非常勤版」など本文がほぼ同一で適用対象だけ違う文書対(19組)は BM25 でも埋め込みでも
  区別不能 → 正規表現ベースの属性抽出で「属性不一致ペナルティ」を検索スコアに加算。
  **決定論的・ゼロコスト・説明可能**、読み取れない文書は中立(誤除外しない)という設計方針が秀逸
- **DefectReport への適用**: 「機械A/機械B」「切削工程/塗装工程」「重要度」など、類似報告書の取り違えに同じ構図が
  ある。クエリと報告書の双方から機械名・工程・4M をファセット抽出して突き合わせる層を追加
- **セミナー対応**: 「AIを使わない方が良い場面」の教材として価値大

### A-4. 決定論的な検索評価ハーネス
- **先方の方針**: LLM-as-judge(RAGAS)は再現性が低い(Drift 0.73)ため、**設定判断は決定論的指標で行う**。
  クエリ100件×6パターン(タイトル/質問文/キーワード/言い換え/本文一文/部分一致)を seed 固定で自動生成し、
  Recall@k / MRR / nDCG@10 で比較。この土台があったから OpenSearch 不採用・リランク廃止を数字で断言できた
- **移植**: 模擬データ100件から同方式でクエリを自動生成する `bench_search.py` を作成。チューニングの授業
  (第4回)で「変更→数字で確認」のループを受講者に回させる

## 優先度B: 運用・品質保証(発展トピックの実装例)

### B-1. RAGAS + Langfuse による回答品質監視
- **先方**(`bench_ragas.py`): Faithfulness(幻覚)/Answer Relevancy/Context Precision/Recall の4指標+Drift。
  巧妙なのはコンテキスト取得方法で、**chatが返す traceId から Langfuse の tool span 出力を引く**ため、
  アプリに評価用の口を増やさない。スコアは同じ trace に書き戻し、UIで「どの回答が幻覚か」を追跡できる
- **移植**: docs/07(発展トピック)の RAGAS 項の具体実装としてそのまま参考になる。Langfuse は docker-compose
  1ファイル(`langfuse/`)で立つ
- **付随**: `eval/fabrication_probe.py`(存在しない規則をわざと聞いて幻覚を誘発するプローブ)は、
  DefectReport でも「存在しない報告書IDを聞く」テストとしてそのまま移植可能

### B-2. 実験ノート文化
- **先方**: `docs/experiment_notebook.md`(時系列・失敗した施策も残す)+`docs/retrieval_tuning.md`(主題別の結論
  と再現手順)+`eval/`(生JSON・ログ)の3点セット。「なぜこの設定なのか」に全て実測の根拠がある
- **移植**: ファイル構成をそのまま真似るだけ。セミナー後半の自社課題でも受講者に書かせたい型

### B-3. 運用スクリプト
- `scripts/start_all.sh`: 4サービスの冪等起動+30分毎cronのウォッチドッグ(落ちていたら再起動)
- SSOセッションの自動再ログイン、web/pipeline 間の INGEST_TOKEN 認証、秘密情報の完全分離(.env.example方式)
- **移植**: DefectReport の docker-compose 運用にウォッチドッグと ingest cron の型を追加(第6回の運用の話の実例)

## 優先度C: 発展・研究ネタ

- **C-1. 多段検索(引用グラフ展開)**: 規程の引用関係グラフをたどる multihop 検索(162件で評価済み)。
  DefectReport なら「同一機械・同一現象の過去対策」を報告書間リンクとしてグラフ化する発展に対応
- **C-2. エージェントハーネス比較**(`agentic/agent_server.py`): 素朴なツールループ(最大6周)と LangChain
  deepagents(計画・サブエージェント・仮想FS)を、検索ツール・LLM を固定して比較する A/B 設計。
  「実測ではほとんど1〜2回のツール呼び出しで終わる=計画は要らなかった」という知見自体が教材になる
- **C-3. ローカルLLMの役割分担**(Ollama): チャット qwen3.5:35b / 要約 gemma3:4b / 検索語拡張 /
  リランク / 埋め込み qwen3-embedding:0.6b と、タスク別に最小のモデルを割り当てる構成。
  機密データを外に出せない企業向け構成の実例(第3回発展・第6回自社展開で紹介)

## 採用を見送るべきもの(先方の実測が根拠)

| 項目 | 理由 |
|---|---|
| **LLMリランク** | nDCG 0.701 vs 無し0.704 で改善なし、しかも44倍遅い(31ms→1,387ms)。先方も実質不採用 |
| **OpenSearch 導入** | 全指標で自作ハイブリッドに負けた。数万チャンク規模・横断検索・高頻度増分更新になったら再検討 |
| **HNSW近似索引** | 数千件規模では numpy 全探索の方が速くて同精度。Chroma のままで問題ない |
