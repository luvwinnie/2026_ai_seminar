# 試験・運用仕様書

> 仕様書 v5.0（第6回(完成形＝例アプリ)）。前の版から変わったところは `変更点.md`。

本書は、DefectReport AI の受け入れ条件（AC）と確かめ方、AI の回答の評価、試験、運用の決まりを定める。
要件の番号（FR・NFR）は `01_要件定義書.md` のもの。
期待値は、模擬データ `data/defect_reports.csv`（110件、発生日 2025-04-07〜2026-03-15）から数えた値である。

---

## 1. 確かめ方の決まり

- 1つの受け入れ条件は「操作」「期待値」「確かめ方」を組で書く。
- 番号は `AC-v10-01` のように、その条件が入った版と連番で付ける。後の版でも番号は変えない。
- 後の版で期待値が変わる条件（道具の本数など）は、同じ番号のまま、その版の値を書く。
- 前の版の条件は、後の版でも満たす。
- 期待値は、元データ `data/defect_reports.csv` から pandas で数えて書く。計画や資料の数字は写さず、必ず検算する。
- API で値を確かめてから、画面で同じ値が出ることを確かめる。
- 「0件」と「失敗」は別の結果として扱う。0件は条件に合う報告書が無いこと、失敗は値を取れなかったことである。
- 確かめた結果は、日付・コマンド（または操作）・件数や値を組で残す。
- 基準の URL は、API が `http://localhost:8000`、画面が `http://localhost:5173`。ポートを変えたときは読み替える。
- Docker で動かすときは、ポートを環境変数 `BACKEND_PORT`・`FRONTEND_PORT` で変えられる（5章）。
- 「例アプリには未実装」は、講座で作るアプリに求めるが、完成形の例アプリにはまだ入っていない条件を示す。例アプリの今の振る舞いを添える。
- 【LLM】を付けた確かめ方はモデルを呼ぶので、料金がかかる。先に LLM を通さない確かめ（API、MCP の道具の直接呼び出し）で道具が返す値を確かめ、LLM を使う確かめは回数を決めて行う。
- 報告書を書き換える確かめ（登録・更新・削除、書き込みを頼むチャット）は、一時の DB か、終わったら元に戻せる環境で行う。講座で共有する DB では行わない。

```python
import pandas as pd
df = pd.read_csv("data/defect_reports.csv")

len(df)                                                     # 110
(df.machine_name == "a61nx").sum()                          # 3
d.between("2025-09-01", "2025-09-30").sum()                 # 7（両端を含む）
df[(df.machine_name == "a61nx") & d.between("2025-09-01", "2025-09-30")].defect_id.tolist()  # ['KZ25-0043']
((df.machine_name == "a61nx") & d.between("2025-10-01", "2025-10-31")).sum()                  # 0
df[["customer", "process", "machine_name", "operator_name", "phenomenon", "factor"]].nunique()
# customer 10, process 8, machine_name 10, operator_name 29, phenomenon 12, factor 10
```

MCP の道具を LLM を通さずに呼ぶコード（AC-v20-05・06。料金なし）：

```python
import asyncio
from fastmcp import Client

async def main():
    async with Client("http://localhost:8000/mcp/") as c:
        print(len(await c.list_tools()))                     # 道具の本数（AC-v20-05）
        r = await c.call_tool("get_defect_report", {"defect_id": "KZ25-0043"})
        print(r.data["machine_name"], r.data["defect_rate"]) # a61nx 0.25
        r = await c.call_tool("get_defect_report", {"defect_id": "KZ25-9999"})
        print(r.data)                                        # {'error': 'KZ25-9999 は見つかりません'}
        r = await c.call_tool("list_defect_reports", {"phenomenon": "表面キズ", "limit": 1})
        print(r.data["total"])                               # 38
        r = await c.call_tool("get_statistics", {})
        print(r.data["kpi"]["total_reports"])                # 110

asyncio.run(main())
```

```python
import pandas as pd
df = pd.read_csv("data/defect_reports.csv")
dfc, prod = df.defect_count.sum(), df.production_count.sum()   # 1829, 10460
dfc / prod, 1 - dfc / prod        # 0.174857（不良率）, 0.825143（FPY）

df.phenomenon.value_counts().head(3)              # 表面キズ 38, バリ残り 14, 穴位置ずれ 12
m = df.assign(month=df.occurrence_date.str[:7]).groupby("month")[["defect_count", "production_count"]].sum()
p_bar = m.defect_count.sum() / m.production_count.sum()
sigma = (p_bar * (1 - p_bar) / m.production_count) ** 0.5
m["p"] = m.defect_count / m.production_count
m["ucl"], m["lcl"] = p_bar + 3 * sigma, (p_bar - 3 * sigma).clip(lower=0)
m[(m.p > m.ucl) | (m.p < m.lcl)]                  # 7か月
```

## 3. 評価仕様

AI の回答を、固定の問題で採点する決まり。直す前と後を、同じ問題で比べるために使う。

### 3.1 評価セット

- `eval/dataset.json` を使う。`eval/make_dataset.py` が `data/defect_reports.csv` から乱数 seed=0 で作る（同じ CSV なら同じ問題になる）。データを作り直したら、このスクリプトも実行し直す。
- 今の評価セットは110件のデータから作った100問で、6つのカテゴリに分かれる。

| カテゴリ | 問の数 | 例 | 必要な道具 |
|---|---|---|---|
| fact（事実） | 30 | 「KZ25-XXXX の使用機械はどれですか?」 | get_defect_report・list_defect_reports・search_defect_reports のどれか |
| aggregate（集計） | 22 | 「報告書は全部で何件登録されていますか?」→ 110、「汎用フライスの報告書は全部で何件ありますか?」→ 46、「状態が未対応(open)の報告書は何件ですか?」→ 4 | get_statistics・list_defect_reports のどれか |
| semantic（意味） | 12 | 「『…』という内容に該当する報告書はどれですか?」（不具合内容の先頭42文字） | 求めない（事前の検索で代わる） |
| fabrication（存在しない） | 10 | 「KZ25-9999の内容を教えてください。」「TXG-9000という機械で発生した不良を教えてください。」 | データの道具（名前や工程を聞く問は list_masters・get_statistics も可） |
| ui（画面操作） | 15 | 「サマリー画面にして」「ダークモードにして」 | ui_navigate・ui_open_report・ui_set_theme など |
| multiturn（会話の続き） | 11 | 前の1〜2問のあとに「KZ25-XXXX を画面で開いて」 | 同上 |

- 固定5問（AC-v30-01）も、同じ採点の考え方で1問ずつ手で採点する。

### 3.2 実行

```bash
cd example_app
.venv/bin/python eval/run_eval.py                 # 全問（判定器も使う）
.venv/bin/python eval/run_eval.py --no-judge      # 判定器を使わない（判定器の料金がかからない）
.venv/bin/python eval/run_eval.py --only aggregate,fabrication --limit 5
```

- 動いているアプリの `POST /api/chat/stream` に1問ずつ送る。宛先は環境変数 `APP_URL`（既定 `http://localhost:5373`）。全問でチャットを100回以上呼ぶので、料金がかかる。
- 判定器は OpenRouter のモデル（環境変数 `JUDGE_MODEL`、既定 `openai/gpt-4o-mini`）で、キーは `example_app/.env` の `OPENROUTER_API_KEY` を読む。
- 出力は `eval/results.json`（問ごとの回答・呼んだ道具・引用・判定）と `eval/report.md`（カテゴリごとの表）。
- 空の応答と一時的なエラーは3回まで送り直す。基盤の揺れとモデルの失敗を分けるため。
- 実行の前に、`/health` の reports が110で、DB と索引の突き合わせ（AC-v31-05）が合格していることを確かめる。

### 3.3 採点規則（答え・道具・引用を分ける）

| 観点 | 値 | 判定 |
|---|---|---|
| 道具 | `tool_ok` | 問ごとに決めた「必要な道具」の組のそれぞれで、1つ以上を実際に呼んだ。道具の名前は接頭辞 `defect-reports_` を外して比べる |
| 引用 | `citation_valid` | 回答の KZ25-XXXX がすべて実在する。質問で聞いた存在しない番号（否定のための言及）と、「例：」「など」の中の例示は数えない |
| 虚偽の操作報告 | `false_claim` | 「表示しました」「開きました」「切り替えました」「並び替えました」などと書いたのに、ui_* を1つも呼んでいない |
| 答え（fact・aggregate・semantic） | `correct` | 期待値の文字列を含む（NFKC で正規化。日付は「2025年9月13日」の和表記も可）∧ `tool_ok` ∧ 虚偽の操作報告が無い |
| 答え（fabrication） | `correct` | 否定の表現（「見つかりません」「存在しません」「該当なし」など）がある ∧ 実在しない番号を引用していない ∧ `tool_ok` |
| 答え（ui） | `correct` | `tool_ok` ∧ 虚偽の操作報告が無い |
| 答え（multiturn） | `correct` | `tool_ok` ∧ 虚偽の操作報告が無い ∧ 期待値を含む ∧ 正解の報告書以外の客先名を出さない |
| 判定器 | faithfulness・relevancy（0〜1） | fact・aggregate・semantic だけ。文脈は正解の行・引用した行・集計の正解で、実際に取得した文書ではない（Ragas の Faithfulness とは別のもの） |

- 答え・道具・引用の率は、カテゴリごとに別々に出す。1つの点数にまとめない。

### 3.4 失敗の分類

不正解の問は1問ずつ読み、次のどこで失敗したかを書く。

| 分類 | 例 | 直す場所 |
|---|---|---|
| 取込（データ） | 帳票の値が違ったまま登録された。索引が DB と合っていない | 取込の確認、索引の突き合わせ |
| 検索 | 言い換え（Q1）で正解が上位に来ない | 同義語・候補数・ファセット |
| 道具の選択 | 件数を検索の上位で数えた（Q5）。画面を ui_* なしで操作したと言った | 指示（AGENTS.md）・道具の説明 |
| 引数 | 機械名の表記違いで0件になった。指定された条件を黙って外した | マスタで表記を確かめる、名前の解決 |
| 生成 | 前のターンから内容を作った（捏造）。存在しない機械を似た機械に読み替えた | 指示、内容を言うときはそのターンで道具を呼ぶ |
| 評価器 | 正しい回答を採点器が不正解にした。誤った回答を正解にした | 採点規則、固定の回答例での確かめ |
| 基盤 | 空の応答、残高切れ（402）、時間切れ | 送り直し、error の扱い |

### 3.5 直す前と後の比べ方

- 同じ `dataset.json`・同じモデル（`OPENCODE_MODEL`）・同じ判定器・同じデータ（110件、索引の突き合わせが合格）で比べる。
- 一度に変える条件は1つにする。直したときに問を易しく書き換えない。
- 全問を同じ条件で1回通した結果どうしを比べる。条件の違う回の結果を足し合わせて1つの点数にしない。
- カテゴリごとの答え・道具・引用の率と、正誤が変わった問の一覧を並べる。
- 回ごとに、日付・モデル・判定器・問の数・コマンドを記録し、`results.json` を回ごとに残す。
- 110件のデータで測った点数は、まだ無い（`eval/report.md` に残る表は、データを110件にする前に測ったもの）。測ったら、上の組で書く。

- モデルは `.env` の `OPENCODE_MODEL`（既定 `anthropic/claude-sonnet-4.5`）で決める。

### 5.3 初回のシード

- 起動時に DB の報告書が0件なら、`/seed-data/defect_reports.csv` から110件を入れ、続けてマスタ（既定の語彙とデータの値）を入れる。索引は裏で DB の全件から作る。
- DB に1件でもあれば入れ直さない。CSV を変えても、今の DB は変わらない。
- 確かめ：`/health` の reports 110、`GET /api/masters` の項目の数（AC-v11-06）、スマート検索の search_mode が hybrid、索引の突き合わせ（5.5）。

### 5.4 停止と復旧

| したいこと | コマンド | 残るもの・注意 |
|---|---|---|
| 止める | `docker compose down` | volume は残る。報告書・索引・会話・Trace はそのまま |
| 全部消す | `docker compose down -v` | 3つの volume を消す。次の起動で110件を入れ直し、索引も作る。会話・CAPA・8D・週次・評価・写真・トリアージの記録・Trace は消える。人が手で行い、AI には実行させない（Hook で止める） |
| backend のコードを直した | `docker compose up -d --build backend` | コードはイメージに入る |
| MCP の道具を直した | 上に加えて `docker compose restart opencode` | OpenCode は起動時に道具の一覧を読む |
| AGENTS.md・opencode.json を直した | `docker compose up -d --build opencode` | どちらもイメージに入る |
| backend のイメージを作り直す | `docker compose build backend` | `app/backend/data/` はイメージに入れない（`.dockerignore`）。古い索引や DB がイメージに入ると、空の volume に写って古いデータが戻る |

### 5.5 索引の突き合わせと作り直し

- 起動のあと、データを入れ替えたあと、評価の前に、DB と索引を突き合わせる。

```bash
docker compose exec backend python -c "
from database import SessionLocal
from models import DefectReport
from services import rag
db = SessionLocal()
ids = {i for (i,) in db.query(DefectReport.defect_id)}
idx = set(rag._get_collection().get(include=[])['ids'])
print('DB', len(ids), '索引', len(idx), '共通', len(ids & idx), '索引だけ', len(idx - ids), 'DBだけ', len(ids - idx))
"
# DB 110 索引 110 共通 110 索引だけ 0 DBだけ 0
```

- ずれていたら、索引だけを作り直す。backend を止め、volume の中の索引のフォルダを消してから起動する。起動時に索引が0件なので、DB の全件から作る。

```bash
docker compose stop backend
docker compose run --rm --no-deps backend rm -rf /app/data/chroma
docker compose start backend
```

### 5.6 観測（Trace）

- Langfuse の画面は `http://localhost:3390`（初期のユーザーは compose に書いたもの）。`LANGFUSE_*` が無い、または届かないときは、記録だけを飛ばしてアプリは動く。
- 残すもの：チャット1問で1トレース `chat`（input は質問、session は `chat-session-{id}`）。子は span `rag_sources`（取得した ID とスコア）と generation `opencode`（モデル名、回答の先頭4000文字、使った道具の名前、エラー）。画面の「役に立った」「問題を報告」は、同じトレースのスコア `user-feedback`（+1・−1）。トリアージは実行ごとに1トレース `triage` で、Jev の呼び出しはトークンと費用を持つ generation。判断モデルによる強化を有効にしたときは、`chat` の子に span `route`（質問の種類と確率）と span `citation_support`（引用の確かめ）、同じ名前のスコア（確かめた組のうち根拠ありの割合）も残す。
- 計っていない区間：OpenCode の中の LLM の呼び出しと MCP の道具の実行は、別の span になっていない。generation `opencode` の input は null、トークンは0、時間は0で、1問の時間のうちどこが遅いかは Trace からは言えない。未計測の区間は「未計測」と書き、記録が無いことを「エラーが無い」と読まない。

### 5.7 モデルと閾値の固定（報告書トリアージ・判断モデルによる強化）

- トリアージは `JEV_ENABLED=1` のときだけ動く（既定は0で、API は503、画面には出ない）。有効にするには `JEV_ENABLED=1 docker compose up -d --build backend frontend`。
- 判断モデルは版を固定する：`DECISION_MODEL` の既定は `typesafe/jev-1.13-20260917`（TypeSafe に直接つなぐときは `jev-1.13.0`）。版の動く名前（`jev-latest`）は使わない。
- 閾値は `app/backend/services/triage_thresholds.json` にある。2026-09-27 に110件で測り、測ったモデル（`typesafe/jev-1.13-20260917`）と質問の指紋（`criteria_hash`）を一緒に記録している。答えたモデルの版が測った版と違えば、測り直すまで自動では採らない。
- 測り直すのは、モデルの版・質問（選択肢や説明）・データを変えたとき。`cd example_app && .venv/bin/python eval/jev_triage_eval.py`（結果は `eval/jev_triage/report.md`、料金は約0.05ドル）。`--reuse` を付けると、前の答えで採る決まりだけを選び直す（料金なし）。
- 不具合内容と原因の文は外部のサービスに送られる。実データで使う前に、送ってよい情報か確かめる。
- 判断モデルによる強化（`DECISIONS_ENABLED=1`）のモデルと閾値は `app/backend/services/decisions.py` の `DECISION_PROFILE` にある（2026-10-18 に `eval/decisions_1018/` で測って決めた。結果は `report.md`）。モデルを替えたら（`DECISION_MODEL_<機能>`）、同じ問題で測り直す（確率の出方はモデルで違う）。
- チャットのモデル（`OPENCODE_MODEL`）を変えたら、評価（3章）を測り直し、モデル名を結果と一緒に記録する。
