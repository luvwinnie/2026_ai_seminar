# DefectReport AI — データモデル設計書

本書は example_app(セミナー版 DefectReport AI)のデータモデル定義。バックエンド・フロントエンド・模擬データ生成はすべて本書のフィールド定義に従うこと。

## 1. ストレージ構成

リレーショナルDBは **PostgreSQL / SQLite の二段構え**(AIチャット履歴DBのベストプラクティス調査に基づく)。同一スキーマで、環境変数 `DATABASE_URL` の有無で切り替わる。

| ストア | 用途 | 実体 |
|---|---|---|
| RDB(PostgreSQL) | 全データの正本(報告書・マスタ・**チャット履歴**)。`DATABASE_URL` 設定時 | Docker Compose の `db` サービス(`postgres:16-alpine`)。`DATABASE_URL=postgresql+psycopg://app:app@db:5432/defectreport` |
| RDB(SQLite) | 同上。`DATABASE_URL` 未設定時のフォールバック(Docker なしの受講者向け) | `app/backend/data/defect_reports.db`(env `DB_PATH` で上書き可) |
| Chroma (PersistentClient) | RAG用ベクトル索引 | `app/backend/data/chroma/`(RDB とは別で常にファイル。Docker では backend の volume に永続化) |

- RDB のテーブル: 報告書 `defect_reports`(§2)、ドロップダウン選択肢マスタ(§2.5)、チャット履歴 `chat_sessions` / `chat_messages`(§2.6)。SQLAlchemy モデルで両DB共通。
- 実装: `database.py` が `DATABASE_URL` があれば `create_engine(DATABASE_URL, pool_pre_ping=True)`、無ければ SQLite(`check_same_thread=False`)。
- Neo4j / Qdrant は使用しない(発展トピックとしてドキュメント記載のみ)。

## 2.5 テーブル: masters

ドロップダウン選択肢を管理するマスタ。SQLAlchemy モデル `MasterItem`(`models.py`)。API 仕様は `docs/04_API設計書.md` §2.5。

| カラム | 型 | 必須 | 説明 |
|---|---|---|---|
| id | INTEGER PK AUTOINCREMENT | ✅ | 内部ID |
| category | TEXT | ✅ | カテゴリ(下表の6種) |
| name | TEXT | ✅ | 選択肢の表示名 |
| sort_order | INTEGER |  | 表示順(既定 0、昇順) |
| is_active | BOOLEAN | ✅ | 有効フラグ(既定 true)。false は新規入力の候補から除外 |
| created_at | DATETIME | ✅ | 登録日時(サーバ付与) |

制約: `UNIQUE(category, name)`(同一カテゴリ内で名称は一意)。

カテゴリ ⇔ `defect_reports` カラム対応:

| category | 対応カラム | 帳票項目 |
|---|---|---|
| `customer` | customer | 客先 |
| `process` | process | 発生工程 |
| `machine` | machine_name | 使用機械 |
| `operator` | operator_name | 作業者名 |
| `phenomenon` | phenomenon | 現象分類 |
| `factor` | factor | 要因 |

- `severity` / `status` / `category_4m` は固定列挙(§2)のためマスタ対象外。
- **自動登録**: 報告書保存時、上記カラムの値がマスタ未登録なら `is_active=true` で自動登録する。
- **リネーム伝播**: マスタ名称の変更は、対応カラムを持つ既存報告書の値へ伝播更新する(`docs/04` §2.5、`updated_reports` に件数)。machine/process/phenomenon/customer は Chroma メタデータにも含まれるため該当報告書を再 upsert する。
- 初期シード時、`data/defect_reports.csv` に出現する各値からマスタを構築してよい(sort_order は出現順や名称順で付与)。

## 2.6 テーブル: chat_sessions / chat_messages

AIチャットの会話履歴をセッション単位で永続化する。会話(セッション)+メッセージの2テーブル構成で、assistant メッセージのメタデータ(参照ソース・ツール実行・推論)は JSON 文字列で保持する(AIチャット履歴DBの標準的な構成)。API は `docs/04` §6。

### chat_sessions

SQLAlchemy モデル `ChatSession`。

| カラム | 型 | 必須 | 説明 |
|---|---|---|---|
| id | INTEGER PK AUTOINCREMENT | ✅ | セッションID |
| title | TEXT |  | タイトル(先頭メッセージの先頭30文字。空なら「新しい会話」) |
| created_at | DATETIME | ✅ | 作成日時(server_default now) |
| updated_at | DATETIME | ✅ | 更新日時(メッセージ追加時に更新。一覧はこの降順) |

### chat_messages

SQLAlchemy モデル `ChatMessage`。

| カラム | 型 | 必須 | 説明 |
|---|---|---|---|
| id | INTEGER PK AUTOINCREMENT | ✅ | メッセージID |
| session_id | INTEGER FK→chat_sessions.id (ON DELETE CASCADE, index) | ✅ | 所属セッション |
| role | TEXT | ✅ | `user` / `assistant` |
| content | TEXT | ✅ | 本文 |
| sources_json | TEXT |  | 参照報告書(§6 の `sources` と同形の JSON 配列文字列。assistant のみ) |
| tools_json | TEXT |  | MCP ツール実行の最終状態(`[{name,status,title}]` の JSON 文字列。assistant のみ) |
| thinking | TEXT |  | 推論テキスト(蓄積。assistant のみ) |
| created_at | DATETIME | ✅ | 作成日時(server_default now)。並びは created_at→id 昇順 |

- 履歴は**サーバー側**で直近20件をロードしてプロンプトに畳み込む(クライアントからの履歴送信は使わない)。
- `chat_messages` は `session_id` に FK(CASCADE)+ index。セッション削除時はメッセージも削除する。
- 返却時、`sources_json` / `tools_json` はパースして `sources` / `tools` として返す(`ChatMessageOut`)。

## 3. Chroma コレクション: defect_reports

- ドキュメント: `"{defect_description}\n原因: {cause}\n対策: {countermeasure}"`
- id: `defect_id`
- metadata: `{defect_id, occurrence_date, machine_name, process, phenomenon, severity, part_name, customer}`
- 埋め込み: `intfloat/multilingual-e5-small`(sentence-transformers)。文書側は `"passage: "`、クエリ側は `"query: "` プレフィックスを付ける。
- sentence-transformers が利用不可の環境では SQLite の LIKE 検索にフォールバック(結果に `search_mode: "keyword"` を明示)。

## 4. 模擬データ(data/defect_reports.csv)

- 117件。カラム名は §2 の API フィールド名と同一(id, created_at, updated_at, ai_improvement は含めない)。
- 乱数シード固定(seed=774123)で再現可能に。世界観・採番は data/fictional_world.json が正(完全架空、ID: KZ25-XXXX)。
- 分布の目安: 期間は 2025-04-01〜2026-03-31 の1年間。機械別・工程別に偏りをつける(パレート図が意味を持つように、現象の上位3種で全体の約6割)。再発 約15%。severity は critical 10% / high 25% / medium 40% / low 25%。
- 帳票ファイル: `data/forms_xlsx/KZ25-XXXX.xlsx`(全件)と `data/forms_pdf/KZ25-XXXX.pdf`(先頭10件、OCRデモ用)。フォーム項目は一般的な製造業の不適合報告書の様式に準拠(発見者名・発生工程・使用機械・作業者名・加工数・部品番号・部品名称・費用欄・不適合数・手順書有無・不具合内容・良品状態・現象/原因・対策)。
