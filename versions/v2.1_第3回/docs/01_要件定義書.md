# DefectReport AI — 要件定義書

> 仕様書 v2.1（第3回の終わり）。前の版から変わったところは `変更点.md`。

本書は、製造業の不適合報告書（不良報告書）を扱う Web アプリ **DefectReport AI** の要件を定義する。講座（全6回）の第2回から第6回で、同じアプリを回ごとに育てる。本書の各版は、その回の時点のアプリの姿を書く（版と回の対応は §10）。

関連文書:
- `00_帳票の調査.md` — 元の帳票（Excel 110件）の様式・項目とセル・表記の揺れ・欠損・件数
- `02_機能仕様書.md` — 機能ごとの画面・操作の流れ・入出力・エラー時の動き、ユースケース
- `03_データモデル設計書.md` — 表と列の定義（正本）、用語表と関係図
- `04_API設計書.md` — REST と SSE の入出力（正本）
- `05_UI設計書.md` — 画面一覧・画面遷移・各画面の状態
- `06_AI設計書.md` — AI の使い方（OpenCode、MCP の道具、プロンプトとガードレール）
- `07_試験・運用仕様書.md` — 受け入れ条件（AC）と確かめ方

## 1. 背景

製造業の品質保証（QA）の現場では、不良や不具合が起きるたびに不適合報告書（NCR: Non-Conformance Report）を作る。報告書には、発生日・客先・工程・機械・作業者・部品・数量・不具合の内容・原因・対策・損失の費用など、品質改善に直結する情報がある。しかし、次の課題がある。

| # | 課題 | 具体的な状況 |
|---|---|---|
| 1 | 報告書が Excel のまま埋もれている | 1件1ファイルの帳票が個人のフォルダやファイルサーバーに散らばり、横断して集計・検索できない |
| 2 | データにする手間 | 集計するには誰かが Excel から転記する必要があり、手間がかかり、写し間違いも起きる |
| 3 | 過去の事例を活かせない | 「同じ機械で似た不良が前にあったか」を調べる手段がなく、人の記憶に頼っている |
| 4 | 原因の分析（4M）が人によって違う | Man／Machine／Material／Method のどれが原因かの分類と改善の案が、担当者の経験でばらつく |
| 5 | 経営層が全体の傾向をつかめない | 不良率の推移、損失の金額、機械や工程の偏り、再発の兆しが見えず、判断が遅れる |

「帳票 → データ → 知見 → 判断」の流れが途中で切れている。本アプリは、この流れを段階的につなぐ。

---

## 2. 目的

DefectReport AI は、この版で次のことを実現する。

1. **報告書をデータにして探せるようにする** — 帳票（Excel）110件の内容を DB に入れ、一覧と詳細で、条件を組み合わせて探せるようにする。
2. **報告書を根拠に答える** — AI アシスタントが道具（MCP）で報告書を取りに行き、報告書番号を示して答える。会話は保存し、あとから開き直せる。AI は画面の移動もできる（画面の移動は**第3回では作らない（後の回）**）。

講座の目的としては、受講者がこのアプリを題材に「仕様書を先に書く → AI（Claude Code）に作らせる → 確かめる → 見つかった穴を仕様書に戻す」流れを、回ごとに繰り返して身につけることにある。

## 3. 対象ユーザー

本アプリはログインを持たない（演習用）。次の3つの利用者像を想定する。画面は利用者像で制限しない。

| 利用者像 | 立場 | 主な関心 | この版で主に使う機能 |
|---|---|---|---|
| 品質保証担当（QA） | 品質保証部門 | 不良の原因の究明、過去の事例の調査、対策の立案 | 報告書の一覧・詳細、AI アシスタント |
| 経営者・管理者 | 工場長・経営層 | 全体の傾向、損失の金額、リスクの早い把握 | 報告書の一覧、AI アシスタント（件数や傾向を聞く） |
| 現場担当 | 製造・検査 | 起きた不良を早く記録する | 報告書の一覧・詳細（記録は帳票の Excel で行う） |

## 4. システム全体像

手元の PC で、フロントエンドとバックエンドを別々に起動して使う。第3回からは Docker Compose で backend・frontend・opencode の3つをまとめて起動する形も持つ（§4.1）。

```mermaid
flowchart LR
    U["利用者（ブラウザ）"] --> FE["フロントエンド<br/>React + TypeScript（Vite）"]
    FE -->|"/api, /health"| BE["バックエンド<br/>FastAPI（Python 3.12）"]
    BE --> DB[("SQLite<br/>報告書・マスタ・会話")]
    CSV["data/defect_reports.csv<br/>（110件）"] -->|"空の DB に自動で入れる"| BE
    BE -->|"HTTP"| OC["OpenCode<br/>（opencode serve）"]
    OC -->|"推論"| LLM["OpenRouter（既定）<br/>ローカル LLM（任意）"]
    OC -->|"MCP の道具<br/>/mcp/"| BE
    BE -.->|"1問1トレース（任意）"| LF["Langfuse"]
```

技術スタック:

| 層 | 技術 |
|---|---|
| フロントエンド | React 19 + TypeScript（Vite）・MUI・React Router・react-markdown。絞り込みの状態は URL クエリに持つ（人の操作と AI の画面操作が同じ URL を見る） |
| バックエンド | FastAPI（Python 3.12）・SQLAlchemy・Pydantic |
| AI | OpenCode（`opencode serve` の HTTP API）＋ OpenRouter（既定のモデル `anthropic/claude-sonnet-4.5`）。ローカル LLM（Ollama など）は `OPENCODE_MODEL` などの環境変数で切り替える（任意） |
| 道具（MCP） | FastMCP を FastAPI に同居（`/mcp/`、名前 `defect-reports`）。道具は15本（第3回で作るのは読み取りの5本だけ。書き込み・画面の操作・業務 Ontology の10本は**第3回では作らない（後の回）**） |
| データ | SQLite（`DATABASE_URL` を設定すれば別の RDB。表は同じ） |
| 観測 | Langfuse（`LANGFUSE_*` を設定したときだけ。無くても動く） |
| 実行 | 手元の PC（Python の venv ＋ npm）。backend はポート 8000、frontend は 5173（`/api` と `/health` を 8000 へ転送）。OpenCode は `opencode serve` を別に起動し、backend に `OPENCODE_URL` で教える。第3回からは Docker Compose でも動かす（§4.1） |

### 4.1 Docker Compose で動かす（第3回から）

第3回からは、3つのサービスを Docker Compose でまとめて起動する。v1.1 の「venv ＋ npm」で起動する形も残す（AI を使わないときや、開発で手早く試すとき）。

| サービス | 中身 | コンテナの中のポート |
|---|---|---|
| `backend` | FastAPI（`/api`・`/health`・MCP の `/mcp/`）。DB（SQLite）は名前付きボリュームに置き、模擬データの CSV は読み取り専用で載せる | 8000 |
| `frontend` | Vite の開発サーバー。`/api` と `/health` を `backend:8000` へ転送する | 5173 |
| `opencode` | `opencode serve`（npm の `opencode-ai` を版を固定して入れる）。MCP は `backend:8000/mcp/` へつなぐ | 4096 |

- Compose のプロジェクト名は `lesson03`。
- PC の外に出すポート（ホスト側の番号）は環境で決める。この演習の PC では API 8120・画面 5220・OpenCode 4120 を使う（コンテナの中は上の表の番号のまま）。
- LLM は、この演習の環境ではローカル LLM（Ollama、モデル `gemma4:26b`）を使う。OpenRouter のキーは置かない。接続先は環境変数（`OLLAMA_BASE_URL`）で渡す（`06_AI設計書.md` §0.3）。
- `opencode` は `backend` が起動して `/health` に答えてから起動する（OpenCode は起動したときに MCP の道具の一覧を読むため）。

## 5. 機能要件（FR）

要件は `FR-<グループ>-<番号>` で識別する。入出力の正確な形は `04_API設計書.md` に書く。

### 5.1 共通（FR-SYS）

| ID | 要件 | 対応 API |
|---|---|---|
| FR-SYS-01 | `GET /health` で稼働状態（`status`）・報告書の件数（`reports`）・AI アシスタントの接続先（`chat_backend`：`opencode`／`none`）を返す | `GET /health` |
| FR-SYS-02 | 起動したとき報告書の表が空なら、模擬データ（`data/defect_reports.csv`、110件）を自動で入れる（シード）。続けて、マスタが空ならマスタを作る（FR-MA-01） | （サーバー） |

### 5.2 報告書（FR-CR）

| ID | 要件 | 対応 API |
|---|---|---|
| FR-CR-01 | 報告書の一覧を表示できる。キーワード（報告書番号・部品番号・部品名・不具合内容の部分一致）・状態・重大度・機械・工程・客先・作業者・現象・4M・期間（発生日）で絞り込み、並べ替え（既定は発生日の新しい順）、ページ送り（既定50件・最大500件）ができる | `GET /api/reports` |
| FR-CR-03 | 報告書の詳細を表示できる。全項目と不良率 `defect_rate`（不適合数 ÷ 加工数）を出す。無い番号は 404 | `GET /api/reports/{defect_id}` |

一覧の決まり:
- 絞り込みの条件は AND で組み合わせる（OR にしない）。
- 期間は発生日を date 型で比べ、両端の日を含む。形の不正な日付（例 `2025-13-01`）や `date_from` > `date_to` は 422 と理由を返す。**例アプリには未実装**（例アプリは形の不正な日付を無視して絞り込まず、`date_from` > `date_to` は 200 で0件を返す）。
- 該当が0件のときは「0件」を表示する（空白にしない）。
- 読み込みに失敗したときは、表と件数を消し、原因と「再試行」を出す。0件の表示と区別する。**例アプリには未実装**（例アプリは原因を出すが、表と「条件に一致する報告書がありません」も残り、「再試行」は無い）。
- 絞り込みの選択肢（機械・工程・客先・作業者・現象）は、画面に書き込まずマスタ（FR-MA-01）から作る。

### 5.3 マスタ（FR-MA）

絞り込みの選択肢は、DB のマスタ（`masters` 表）に持つ。種類は客先（customer）・工程（process）・機械（machine）・作業者（operator）・現象（phenomenon）・要因（factor）の6つ。重大度・状態・4M は決まった値なのでマスタにしない。

| ID | 要件 | 対応 API |
|---|---|---|
| FR-MA-01 | マスタ6種を持ち、種類ごとに返す（各値の使用件数つき）。初回の起動で、取り込んだデータの値から作る。用語は用語表（`03_データモデル設計書.md`）を正本にする | `GET /api/masters` |

### 5.4 AI アシスタント（FR-CH）

AI アシスタントは OpenCode を通して LLM（既定は OpenRouter）で答える。報告書のデータには MCP の道具で触れる。

| ID | 要件 | 対応 API |
|---|---|---|
| FR-CH-01 | 利用者は自然文で質問し、報告書を根拠にした回答を受け取れる。AI は道具（MCP）で報告書を取りに行き、そのターンで道具から取った値だけで答える | `POST /api/chat/stream` |
| FR-CH-02 | 回答を SSE で逐次表示する。イベントは `session`（先頭）・`thinking`（推論）・`tool`（道具の実行の進み具合）・`token`（本文）・`done`・`error`。空の応答・残高切れ（402）・`finish_reason=length`（出力の上限で切れた）は成功にせず、`error` で理由を出す（`finish_reason=length` の見分けは**例アプリには未実装**） | 〃 |
| FR-CH-06 | 会話の履歴は、サーバーが DB から直近20件を読んで AI に渡す（ブラウザは履歴を送らない） | 〃 |
| FR-CH-08 | 利用者がはっきり頼んだときだけ、会話から報告書を登録・更新する（`create_defect_report`：番号は自動・状態は `open` に固定。`update_defect_report`：状態・重大度・対策・原因・要因・4M・備考・良品状態の8項目だけ）。実行したら、番号と変えた項目を報告する。**第3回では作らない（後の回）** | （MCP） |
| FR-CH-09 | 会話をセッションごとに保存し、一覧・復元・削除できる（再読込しても残る）。最初の送信でセッションを作り、題は最初の質問の先頭30文字にする | `GET`・`DELETE /api/chat/sessions[/{id}]` |
| FR-CH-10 | AI は画面を操作できる（`ui_navigate`：ページと絞り込み／`ui_open_report`：詳細を開く／`ui_set_theme`：ライト・ダーク）。画面の状態の正本は URL クエリで、人の操作と AI の操作が同じ URL を見る。操作は画面の移動と表示だけで、データは変えない。画面を操作したと答える前に、必ず `ui_*` を呼ぶ（前のターンで同じ操作をしていても毎回呼ぶ。ターンごとに独立）。**第3回では作らない（後の回）** | `GET /api/ui/events`（SSE） |
| FR-CH-11 | 用語表を機械が読める形にした業務 Ontology（`app/backend/ontology/quality.json`）を、道具で引ける（定義・名前の解決・対象・関係・条件別の集計）。「工程別の件数」のような条件別の件数・損失はサーバーが数える。対象や期間を解決できないときは、範囲を黙って広げずに誤りと理由を返す。**第3回では作らない（後の回）** | （MCP） |

- 例アプリの AI の道具（MCP）は15本（読み取り5・書き込み2・画面の操作3・業務 Ontology 5）。第3回で作るのは読み取りの5本（`list_defect_reports`・`search_defect_reports`・`get_defect_report`・`get_statistics`・`list_masters`）だけ。
- 第3回の AI アシスタントは、独立したページ `/chat` だけで使う。全ページに置く AI パネルは**第3回では作らない（後の回）**。
- 道具の一覧と引数は `06_AI設計書.md` に書く。

## 6. 業務の決まり

要件と画面・AI の答えが、同じ数え方をするための決まり。用語は `03_データモデル設計書.md` の用語表に合わせる。

- 「報告1件」と「不良品1個」を分ける。件数の単位は「件」、不適合数・加工数の単位は「個」。
- 期間は発生日（`occurrence_date`）で数え、両端の日を含む（報告日では数えない）。
- 報告書1件の不良率 `defect_rate` は 不適合数 ÷ 加工数。加工数が0なら null（画面は「—」）。
- 数量の決まり：0 ≦ 不適合数 ≦ 加工数。AI が帳票の文章から取り出した値（構造化出力）の検査に使う（構造化出力とその検査は**第3回では作らない（後の回）**。第3回は元データの110件が決まりを満たすことだけを確かめる）。形の検査（型・必須）と、この業務の決まりの検査を分ける。例アプリでは、業務 Ontology の集計（`query_quality_ontology`）が、この決まりに合わない報告書を数え、合わないものがあれば率を出さない。

## 7. 非機能要件（NFR）

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 動作環境 | 受講者のノート PC で動くこと。外部のサービスは LLM（OpenCode 経由の OpenRouter）だけ。ローカル LLM（Ollama など）への切替は任意で、接続先は環境変数で決める。第3回からは Docker Compose でも動かす（§4.1）。この演習の環境では LLM にローカル LLM（Ollama の `gemma4:26b`）を使う |

| NFR-05 | データの規模 | 模擬データ110件（KZ25-0001〜KZ25-0110、発生日 2025-04-07〜2026-03-15）を前提とする。一覧は既定50件・最大500件 |
| NFR-06 | 再現性 | 模擬データは乱数を固定して生成する（`data/generate_mock_data.py`）。受け入れ条件の期待値は、この CSV から数えた値にする |
| NFR-08 | 読みやすさ | AI が作ったコードを受講者が読んで直せるよう、簡単な構成と名前にする。過度な抽象化をしない |
| NFR-09 | 移植性 | SQLite とローカルのファイルだけで動き、専用のサーバーを要らない。GPU は要らない |
| NFR-10 | 言語 | 画面・データ・AI の回答は日本語 |
| NFR-11 | 観測 | `LANGFUSE_*` が設定されているときだけ、1問を1トレースとして Langfuse に送る（質問・使った道具・回答）。トレースには入力（質問）と使ったトークンを必ず残す（トークンは**例アプリには未実装**。例アプリの AI アシスタントのトレースは質問を残すが、トークンの数は0のまま）。`done` イベントに `trace_id` を入れ、画面の回答とトレースを照合できる。Langfuse が無くても動く。Langfuse への送信は**第3回では作らない（後の回）**。第3回は `LANGFUSE_*` が無いときに記録せずに動き、`trace_id` が null になることだけを確かめる |
| NFR-13 | 画面の幅 | PC の画面（幅 1280px 以上）を前提とする |

## 8. 受け入れ条件（AC）

受け入れ条件の全体（操作・期待値・確かめ方）は `07_試験・運用仕様書.md` に、版ごとの番号（`AC-v10-01` など）で書く。ここには要件ごとの主な期待値を書く。期待値は元データ（`data/defect_reports.csv`、110件）から数えた値にする。

期待値は元データから数えて書く。計画や AI が示した数字は、元データで検算してから使う。「例アプリには未実装」と書いた条件は、完成形の例アプリでも満たしていない（演習で直す対象）。

|---|---|---|
| FR-SYS-01・02 | 空の DB で起動すると `/health` の `reports=110` | AC-v10-01 |
| FR-CR-01 | 機械 a61nx は3件（KZ25-0019・KZ25-0043・KZ25-0056）。2025年9月は7件（KZ25-0042〜KZ25-0048）。a61nx かつ 2025年9月は KZ25-0043 の1件だけ（AND で絞る）。a61nx かつ 2025年10月は0件で、画面は0件を表示する | AC-v10-03〜06 |
| FR-CR-03 | KZ25-0043：発生日 2025-09-13、客先 翠峰重工業、工程 マシニング、機械 a61nx、部品 補機マウントリブ、加工数12・不適合数3、`defect_rate=0.25`（画面 25.00%）、現象 表面キズ、損失合計 60,581円。KZ25-9999 は 404 | AC-v10-07・08 |
| FR-CR-01（期間） | `date_from=2025-13-01` と `date_from` > `date_to` は 422 と理由（**例アプリには未実装**。例アプリは前者が200で110件、後者が200で0件）。`date_from=date_to=2025-09-17` は2件（両端の日を含む） | AC-v11-01〜03 |
