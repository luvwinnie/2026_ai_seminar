# 試験・運用仕様書

> 仕様書 v2.1（第3回の終わり）。前の版から変わったところは `変更点.md`。

本書は、DefectReport AI の受け入れ条件（AC）と、その確かめ方を定める。
要件の番号（FR・NFR）は `01_要件定義書.md` のもの。
期待値は、模擬データ `data/defect_reports.csv`（110件、発生日 2025-04-07〜2026-03-15）から数えた値である。

---

## 1. 確かめ方の決まり

- 1つの受け入れ条件は「操作」「期待値」「確かめ方」を組で書く。
- 番号は `AC-v10-01` のように、その条件が入った版と連番で付ける。後の版でも番号は変えない。
- 後の版で期待値が変わる条件（道具の本数など）は、同じ番号のまま、その版の値を書く。
- 前の版の条件は、後の版でも満たす。
- 期待値は、元データ `data/defect_reports.csv` から pandas で数えて書く。計画や資料の数字は写さず、必ず検算する。
- API で値を確かめてから、画面で同じ値が出ることを確かめる。
- 「0件」と「失敗」は別の結果として扱う。0件は条件に合う報告書が無いこと、失敗は値を取れなかったことである。
- 確かめた結果は、日付・コマンド（または操作）・件数や値を組で残す。
- 基準の URL は、API が `http://localhost:8000`、画面が `http://localhost:5173`。ポートを変えたときは読み替える。この演習の PC（venv ＋ npm でも Docker Compose でも）は API `http://localhost:8120`、画面 `http://localhost:5220`、OpenCode `http://localhost:4120`。
- 「第3回では作らない（後の回）」は、第3回（簡易的な AI アシスタント）では作らず、後の回で作る条件を示す（`01_要件定義書.md` §10.1）。第3回の受け入れでは確かめない。
- 「例アプリには未実装」は、講座で作るアプリに求めるが、完成形の例アプリにはまだ入っていない条件を示す。例アプリの今の振る舞いを添える。
- 【LLM】を付けた確かめ方はモデルを呼ぶので、料金がかかる。先に LLM を通さない確かめ（API、MCP の道具の直接呼び出し）で道具が返す値を確かめ、LLM を使う確かめは回数を決めて行う。この演習の環境（ローカル LLM）では、1回の確かめで10問までにする。
- LLM を通さないチャットの確かめは、OpenCode の HTTP API を差し替えた pytest（`app/backend/tests/fake_opencode.py`）と、同じ応答を返す小さなサーバーを使う画面の試験（`app/e2e`）で行う。
- 報告書を書き換える確かめ（登録・更新・削除、書き込みを頼むチャット）は、一時の DB か、終わったら元に戻せる環境で行う。講座で共有する DB では行わない。

検算のコード（リポジトリの直下で実行）：

```python
import pandas as pd
df = pd.read_csv("data/defect_reports.csv")
d = df["occurrence_date"]                                   # 'YYYY-MM-DD' の文字列
len(df)                                                     # 110
(df.machine_name == "a61nx").sum()                          # 3
d.between("2025-09-01", "2025-09-30").sum()                 # 7（両端を含む）
df[(df.machine_name == "a61nx") & d.between("2025-09-01", "2025-09-30")].defect_id.tolist()  # ['KZ25-0043']
((df.machine_name == "a61nx") & d.between("2025-10-01", "2025-10-31")).sum()                  # 0
df[["customer", "process", "machine_name", "operator_name", "phenomenon", "factor"]].nunique()
# customer 10, process 8, machine_name 10, operator_name 29, phenomenon 12, factor 10
```

## 3. 動かし方と止め方（第3回から）

venv ＋ npm（v1.1 の形）と Docker Compose の2つで動かせる。ポートはこの演習の PC の番号（§1）。

### 3.1 venv ＋ npm

| 手順 | コマンド（リポジトリの直下から） |
|---|---|
| backend | `cd app/backend && .venv/bin/uvicorn main:app --port 8120`（AI を使うときは `OPENCODE_URL=http://localhost:4120` を付ける） |
| 画面 | `cd app/frontend && npm run dev`（5220。`/api`・`/health` を 8120 へ転送） |
| 止める | それぞれ Ctrl+C |

- `OPENCODE_URL` が無いときはチャットが使えない（`/health` の `chat_backend` が `none`、AC-v20-08）。報告書の一覧・詳細はそのまま動く。

### 3.2 Docker Compose

| 手順 | コマンド（リポジトリの直下から） |
|---|---|
| 作って起動 | `docker compose up -d --build` |
| 状態 | `docker compose ps`（backend は healthy、3つとも running） |
| ログ | `docker compose logs -f backend`（opencode・frontend も同じ） |
| 道具を変えたあと | `docker compose restart opencode`（道具の一覧を読み直させる） |
| 止める | `docker compose stop`（コンテナを消すときは `docker compose down`） |

- `docker compose down -v` は使わない（DB のボリュームが消える）。
- このフォルダの Compose（プロジェクト `lesson03`）以外のコンテナには触らない。
