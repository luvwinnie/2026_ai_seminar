# 軽量ローカルモデル全件評価（2026-09-15開始）

結果の入口は [HTMLレポート](report/report.html)。**2026-09-15に全対象の測定・整合性検証を完了した。** [最終検証記録](report/validation.json)に、再採点・保存ベクトルからの検索順位復元・DBとモデルdigestの照合・PC/スマートフォンの表示検証を保存している。

通常APIで生成21タグ×50ケース＝1,050件、会話API未対応のMTP版はraw API＋JSON補助ハーネスで別途50件を実測した。Llama 3.2 Visionは通常/rawの両APIでモデル読込エラーを確認した。埋め込み7タグ×24問×2回＝336件、OCR専用1タグの画像3枚を実行。Gemma 3の出力形式診断48件、Qwen3.5の指示明確化70件、保存済みツール指示210件の実行監査も別枠で残した。ケース数を独立した問題数として合算しない。

## 対象範囲

研究室の Ollama(`OLLAMA_BASE_URL`)にインストールされている43タグを、`/api/tags` と各タグの `/api/show` で確認した。**クラウドを除く保存サイズ20,000,000,000バイト以下の全31タグ**を今回の軽量範囲とする。最終的な用途分類は回答生成23、埋め込み7、OCR専用1。クラウド3、20GB超9タグは対象外。必要RAM・VRAMが20GB以下という意味ではない。全タグ・digest・サイズ・対象理由は [coverage.csv](report/coverage.csv)、テンプレート・パラメータも含む開始時点の生情報は [inventory.json](inventory.json)。

同じ重みの別設定タグもそれぞれ測定する。タグ名・capabilitiesだけでは実行可否を断定しない。completionを申告した24タグの全件に、通常会話と実際のnative tool APIのプローブを送った。`jina-v5:small` は古い一覧でcompletion扱いだったが、今回のmodel metadata/APIで埋め込みモデルとして扱う。

**適用範囲の変更:** Unlimited-OCRは通常Q&Aを8件実行して反復出力を確認した後、公式資料から文書画像専用という用途を確認した。汎用Q&Aの連続測定を打ち切り、日本語の合成文書画像3枚でのOCR動作確認へ切り替えた。変更の時点・根拠は [scope_amendment.json](scope_amendment.json)。元の8失敗記録は残し、生成モデルの順位には混ぜない。その他の生成23タグのプロトコル・問題・設定は変更していない。第一実行区間と再開区間のmetadata・ソースハッシュを照合し、既存の結果を置き換えず統合する。

## 評価設計

基本40問題＋対応する言い換え10件、合計50ケースを各利用可能な生成タグで実行する。50独立問題とは数えない。

Ontology資料読解10問とエージェント実行10問は、同じ業務質問に対して資料をホストが渡すかモデルが取得するかを変えた対応比較である。各区分の成功率を別に報告し、合算した40問の総合順位は作らない。

主表は要求した出力形式を含むタスク成功率である。「値だけの一致」も単一JSONから抽出できた値の補助指標であり、自然文の意味を全件採点したものではない。例えばQwen3.5:2bのO01は正しい根拠と値を自然文で回答したが、要求されたJSON形式に失敗した。こうした区別は[講義用の実測例](lecture_examples.md)で明示する。

| 区分 | 基本問題 | 言い換え | 測るもの |
|---|---:|---:|---|
| RAG固定コンテキスト | 12 | 4 | 正解ID・機械・工程、資料にない質問、未記録項目、資料中の偽命令 |
| Ontology資料読解 | 10 | 0 | ホストが実MCPで事前取得した資料の読み取り。エージェント実行とは別の比較軸 |
| 最初のツール選択 | 8 | 2 | 正しいツールがちょうど1個、正しい型・引数。ここでは実行しない |
| Ontologyエージェント | 10 | 4 | 実MCPを使って対象・条件・関係を正しく確認した上で最終回答 |

前回の117報告を固定したスナップショットと隔離SQLiteを再利用。評価専用3報告・3CAPAにより、関連CAPAの多重結合、率の加重集計、ゼロ分母、NULL損失、曖昧な設備、存在しない設備、CAPAの事前検証を確認する。書き込み・画面操作のツールは実行を遮断し、試行を記録する。`preview_capa_update` は実行するが保存はしない。業務用PostgreSQLやアプリのモデル設定は変更しない。

正解は固定スナップショットの独立計算または明示した評価fixtureから定める。LLM judgeは使わない。JSON Schemaと値の一致、実ツールの呼び出し・返却値を決定論的に検査する。実行したという説明文だけで合格にしない。金額・件数の誤差許容1e-6、比率5e-5。数値文字列やスカラーを配列に包む出力は主指標では不合格。参考として値だけの一致も併記する。余分なフィールド・複数の候補JSONからの正解選択は受理しない。単独のJSONコードブロックは受理する。

Ontologyの同等経路を認める根拠監査は、前回の `analyze.grounded()` を測定前に固定して利用する。今回の結果を見て許容経路を追加しない。正しい条件の集計結果、実際の曖昧候補一覧、CAPA→報告の実外部キーなどを確認する。

## ネイティブとJSON補助ハーネス

`/api/chat` の `tools` が受理されるタグはnative方式で評価する。実際の `message.tool_calls` だけを実行し、モデル本文に書かれたツール風JSONは実行しない。

明示的なHTTP 400 `does not support tools` が返るタグには、別方式の **JSON補助ハーネス** を使用する。モデルに `{"tool_call":{"name":"...","arguments":{...}}}` の出力プロトコルを説明し、ホストが構文・JSON Schema・実行許可を検査してMCPへ渡す。最終回答は `{"final":{...}}`。この方式の成績はnative tool supportの証明にはならない。両方式とも同じ28ツール定義・同じ問題・同じ隔離MCPを使用する。

この実装は、講義で扱う「LLM出力を受け取って検証・ツール実行・履歴への追加・再推論を行うハーネス」の具体例にもなる。OpenCodeの本番画面・全エージェント設定を含むE2E測定ではない。以前のOpenCode実測は [前回レポート](../reports/20260915/report.html) に残す。

## 推論条件

温度0.2、seed 20260915、context 32,768。最大8モデルターン、同じツール同じ引数を3回連続で実行した場合は停止。1リクエスト160秒、1ケース300秒。出力4,096トークン、出力長上限に達したときだけ8,192で同じ要求を1回再送し、元の応答も保存する。Qwen3-VLは事前プローブで `think=false` でも推論出力を観測したため初期上限8,192。その他のthinking対応モデルはfalse、GPT-OSSはlow。Ollamaモデル固有の残りの設定は保存した `show.parameters` を継承するため、純粋な重みのみの比較ではなく、記載した設定での実用評価となる。

## 埋め込み・検索

7タグすべてに実際の `/api/embed` を送る。同じ117文書（本文・原因・対策）と24問を使用。6問は前回のもの、追加18問はこの作業のCodexが別の固定報告を読んで作成した言い換え質問である。独立した人間の評価者による関連性アノテーションは行っていない。正解を見てモデルごとに質問・接頭辞・RRF重みを調整しない。

作成主体の訂正：測定開始時にハッシュを固定した `run_embeddings.py` 冒頭の「human-written」は誤記であり、人間が作成・検証したという意味には扱わない。固定ソースを後から置き換えず、この説明で訂正する。設問・正解は評価対象のOllamaモデルの回答から生成せず、固定報告と明示したfixtureに基づく。採点にLLM judgeは使っていない。

各モデルの公式推奨query/document接頭辞を利用し、文字列を `input` に渡す。Jinaは `Query: `/`Document: `、Nemotron 3は `query: `/`passage: `、EmbeddingGemmaはタスクとtitle/text接頭辞、Qwen3はquery側に検索タスク指示。元の設定ファイル・説明は [references](references/) に保存。タグのLoRA適用状態など、metadataだけで確認できない重みの由来は断定しない。

context 2,048、`truncate:false`、文書は8件ずつ。L2正規化後のcosineで全117件を厳密比較する。ゼロベクトル・NaN/Inf・不正な次元をエラーにする。各質問2回、主結果は1回目、2回目でTop5再現性を確認する。文書とクエリのベクトルをNPZ、全順位とAPI時間をJSONに保存。

バッチ要求がHTTPエラーになった場合は、元のエラーを保存し、同じ入力を1件ずつ再送する。入力内容は変えず、再送時間も索引作成時間に含める。

BM25はアプリと同じアルゴリズム・Sudachiトークン化、k1=1.4、b=0.75。今回は公平な本文比較のため同じ3フィールドのみ、同義語追加なし。RRFはdenseとBM25それぞれ上位50件を `1/(60+rank)` で加算。e5-smallも同じ文書・24問でCPUの比較値を得る。異なるホストのためe5とOllamaの速度の直接優劣は判断しない。

## 実行方法

作業ディレクトリは `example_app`、Pythonは `.venv/bin/python`。

```bash
# 以下は各スクリプトの役割。固定結果の再集計だけならreport.pyのみを実行する。
.venv/bin/python eval/local_llm/light_20260915/report.py
.venv/bin/python -m pytest -q eval/local_llm/light_20260915/test_protocol.py
```

入力・プロトコルを変えて再測定する場合は日付/版の異なるディレクトリを作る。既存結果を上書きして旧結果と混ぜない。

1. 全タグのinventoryを保存し、`preflight.py` で24生成タグの通常会話とnative APIを確認。
2. `prepare_light.py` で50ケース・出力Schema・MCPツール定義を固定。
3. `test_protocol.py` と少数の実MCPパイロットで採点・実行の整合性を確認。
4. `run_generation.py` で生成モデルをサイズ順・推論同時実行数1で測定。ケースごとに一時ファイルからatomic renameで保存。再開はソース・データ・設定のハッシュ一致時のみ。
5. `run_embeddings.py --prepare` はOllamaを使わず、検索データセットとCPUのBM25/e5比較値を準備。
6. 生成測定の完了後に `run_embeddings.py` を実行。GPUの同時利用を避ける完了ガードあり。
7. `report.py` で保存済み結果を集計。追加LLM呼び出しはしない。

実測時はOCRの用途変更により `finish_generation.py` で第二実行区間を作成した。生成測定終了後に `run_after.py` が埋め込み測定→補助診断→レポート再集計を順に実行する。`diagnostics.py` のGemma 3補助実験は4タグ×基本RAG12問を、簡潔な指示＋APIのJSON Schema制約で再測定する。主表の数値は置き換えない。`ocr_check.py` は画像3枚の報告ID・機械名の一致と文字誤り率CERを記録する。OCRの清潔な合成画像3枚は専門タスクの動作確認であり、広範なOCR精度評価ではない。

OCRのCERは、空白・Unicode幅・検出座標/領域ラベル・HTML/Markdownの装飾を正規化した文書テキストの編集距離を正解文字数で割る。座標や罫線の出力形式を認識文字の誤りとして数えない。正規化は画像試験開始前に固定し、実行ソースのハッシュを結果に記録する。

**本文抽出の訂正:** 実応答では検出タグがなく、`header [47, 62, 361, 105]` のような領域接頭辞が残ったため、初期集計が座標等を本文に含めていた。`analyze_ocr.py` はその既知形式を除外し、全3枚の保存済み出力から本文CERを再計算する。元の応答と初期CERは上書きせず、`ocr/analysis.json` に訂正理由・両スコア・抽出テキストを記録する。新たなLLM推論は行わない。3枚とも本文の誤りは「評価」→「評估」の1文字で、報告ID・機械名は一致した。

Qwen3.5の小型5タグには、最終JSONを作る前に必要なツールを実行するよう明記した事後診断を、同じOntology14ケースずつ（計70件）実施する。変更文と全応答は `agent_prompt_diagnostic.json` に保存し、主測定を置き換えない。また、単発ツール選択の保存済み指示を隔離MCPへ再送し、公開Schemaの先にあるアプリ内部の制約も確認する。UI2問は実行せず、参照・事前検証の基本6問について「選択・Schema＋実際の受理」を `tool_execution_audit.json` に記録する。追加のLLM生成は不要で、保存を伴う操作は遮断する。

**会話API未対応タグの追加50ケース:** `qwen3.8:27b-mtp-q4_K_M` は通常の会話APIがunknown rendererエラーだったが、補助プローブで `/api/generate raw:true` から応答できた。この発見後、`run_raw_transport.py` で同じ50ケースを全件測定する追加実験を設定した。先行する全推論の完了を待って直列実行する。ChatMLを手動で整形し、空の閉じたthink区間でassistant応答を開始する。ツールはモデル本文に明示的なJSONプロトコルを指定する補助ハーネスで実行する。ネイティブツールAPIを使えたことにはせず、元の会話APIの測定不能記録と別表にする。設定・採点・実MCPの実行境界は同じだが、テンプレートと通信経路が異なる。全生応答・整形した要求・実ツール結果は `raw_transport.json`。
